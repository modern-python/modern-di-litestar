# Design: Adopt the modern-di integration kit

## Summary

`modern-di` 2.28.0 shipped `modern_di.integrations` — the framework-agnostic
primitives that formalize what this package's `build_di_container` and
`_Dependency` already hand-roll. This change swaps the hand-rolled internals
for kit calls. Public API and runtime behavior are unchanged; two tests that
construct `_Dependency` directly (an internal) must be updated to pass a
`Marker`, since `_Dependency`'s field is renamed.

## Motivation

Third of the 13 adapter conversions surveyed by the kit's own design — see
[modern-di's decision record](https://github.com/modern-python/modern-di/blob/main/planning/decisions/2026-07-13-integration-kit-shape.md).
Like `modern-di-fastapi` (second, native-DI), this package's `FromDI` returns
Litestar's own `Provide`, so this conversion exercises `classify_connection`
and `Marker.resolve()` but not `parse_markers`/`resolve_markers` (no
`@inject` decorator — Litestar's own dependency injection already scans/binds
per parameter).

Concretely, in `main.py` today:

- `build_di_container`'s isinstance-over-`_CONNECTION_PROVIDERS` loop is
  `modern_di.integrations.classify_connection`, byte-for-byte.
- `_Dependency`'s `__call__` body
  (`return di_container.resolve_dependency(self.dependency)`) is
  `modern_di.integrations.Marker.resolve`, byte-for-byte.

**Difference from the fastapi/starlette conversions, found by reading the
actual test suite (not assumed):** `tests/test_routes.py` has two tests —
`test_from_di_dependency_resolves_provider_instance` and
`test_from_di_dependency_resolves_by_type` — that import `_Dependency` and
construct it *directly* with a raw provider/type
(`_Dependency(Dependencies.app_factory)`, `_Dependency(SimpleCreator)`), not
through `FromDI`. Once `_Dependency`'s field is renamed from `dependency` to
`marker: integrations.Marker[T_co]`, these two calls would positionally bind
the raw provider/type to the `marker` field. The provider case would likely
keep "working" by accident (`AbstractProvider.resolve(container)` and
`Marker.resolve(container)` happen to share a call shape when no override is
set), which is worse than an honest break — it would silently stop testing
what it claims to test. The type case would raise `AttributeError` (a bare
type has no `.resolve`), a real failure. Both must be updated to construct
`_Dependency(integrations.Marker(...))`.

## Design

In `modern_di_litestar/main.py`:

- Import `integrations` from `modern_di`.
- `build_di_container`: replace the isinstance loop with
  `match = integrations.classify_connection(request, _CONNECTION_PROVIDERS)`,
  then open the child via
  `async with fetch_di_container(request.app).build_child_container(scope=match.scope if match else None, context=match.context if match else None) as container:` —
  replacing the manual `try`/`finally: await container.close_async()`.
- `_Dependency`'s field changes from `dependency: AbstractProvider[T_co] |
  type[T_co]` to `marker: integrations.Marker[T_co]`; its `__call__` body
  becomes `return self.marker.resolve(di_container)`.
- `FromDI` constructs `Provide(dependency=_Dependency(integrations.Marker(dependency)), use_cache=False)`
  instead of `Provide(dependency=_Dependency(dependency), use_cache=False)` —
  its own signature (`dependency`) is unchanged.

In `tests/test_routes.py`:

- Add `from modern_di import integrations` (or extend the existing
  `from modern_di import ...` import).
- `test_from_di_dependency_resolves_provider_instance`: change
  `_Dependency(Dependencies.app_factory)` to
  `_Dependency(integrations.Marker(Dependencies.app_factory))`.
- `test_from_di_dependency_resolves_by_type`: change
  `_Dependency(SimpleCreator)` to `_Dependency(integrations.Marker(SimpleCreator))`.

No other test file references `_Dependency`, the isinstance loop, or any
other changed internal — `test_groups.py` only imports the unrelated
`_autowired_dependencies` (untouched by this change), and
`test_lifespan.py`/the rest of `test_routes.py` go through the public
`FromDI`.

## Non-goals

- **No `architecture/*.md` edit.** This repo's `architecture/` holds only
  `autowiring.md`, which documents `_autowired_dependencies`'s
  collision-warning and MRO-walk behavior — unrelated to this conversion and
  verified to name none of the changed internals. There is no
  `container-lifecycle.md`/`dependency-resolution.md` here (unlike
  `modern-di-starlette`/`modern-di-fastapi`) to promote into.
- **No `CLAUDE.md` edit.** Its "Key concepts" section describes
  `build_di_container`/`FromDI` at the behavior level ("creates a child
  Container per request/websocket... tears it down"), not by implementation
  mechanism — verified accurate as-is, pre- and post-conversion.
- Any change to `ModernDIPlugin.on_app_init`, `_lifespan_manager`, or
  `_autowired_dependencies` — none of that is part of the kit.
- `integrations.parse_markers`/`resolve_markers` — Litestar has no decorator
  path; its own DI already scans/resolves per parameter.

## Testing

- `just test-ci` — 100% line coverage, all tests green (two tests edited as
  described above; the rest of the suite unmodified).
- `just lint-ci` — ruff (`select=ALL`), `ty check`, `check-planning`.

## Risk

- **Version-floor bump breaks on an environment still resolving `<2.28`**
  (low likelihood — semver-compatible; low impact — `pyproject.toml` pins the
  floor explicitly).
- **The two edited tests mask a real behavior change instead of catching
  one** (low likelihood — both are being changed to construct a real
  `Marker`, which resolves through the exact same
  `container.resolve_dependency` path as before; `Marker.resolve`'s
  equivalence to the old direct call was already verified against the
  installed `modern_di` 2.28.0 source during the fastapi conversion).
